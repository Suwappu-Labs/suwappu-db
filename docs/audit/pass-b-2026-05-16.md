## B1 — Workspace lints alignment

**Verdict:** ✅ Already met.

`Cargo.toml` declares:

```toml
[workspace.lints.rust]
unsafe_code = "forbid"

[workspace.lints.clippy]
all = { level = "deny", priority = -1 }
pedantic = { level = "warn", priority = -1 }
```

Every workspace crate inherits via `[lints] workspace = true`.
No `unsafe { }` block exists in `crates/**/src/**.rs`; the workspace
lint catches any future regression at compile time.

## B4 — Consensus-time clock audit

**Verdict:** ⚠ Accepted — no consensus-time exposure in suwappu-db.

suwappu-db has no consensus path of its own (consensus runs in suwappu-dag,
where `suwappu-node/events.rs:104 SystemTime::now()` is the known issue
the broader plan tracks). The suwappu-db audit catalogues every
`SystemTime::now()` / `Instant::now()` site and confirms none of
them sit on a determinism-load-bearing path.

### Sites audited (production, excludes `#[cfg(test)]`)

| Site | Surface | Risk |
|---|---|---|
| `crates/suwappudb-state/src/metrics.rs:164` `Timer::start` | Observability | None — output never crosses replicas |
| `crates/suwappudb-state/src/snapshot.rs:38` `StateSnapshot::new` (writes `timestamp`) | Snapshot metadata | None — field is informational; snapshot equality is over `state_root` + `encoded_state`, not timestamp |
| `crates/suwappudb-state/src/snapshot.rs:66` `StateSnapshot::is_valid` (freshness gate) | Operational filter | ⚠ Local clock skew can reject otherwise-valid snapshots. Caller-tunable via `max_age_secs`; not a soundness issue. Doc note added inline. |
| `crates/suwappudb-bridge/src/telemetry.rs:23,48,73` `BlockTimer` / `AnchorTimer` / `ParityTimer` | Observability | None |

### Recommendations

1. **No code change needed for suwappu-db's consensus surface** — the
   sites identified are observability or local-only.
2. **Cross-replica determinism** (block MACs, anchor hashes, state
   trees) does NOT pull `SystemTime` / `Instant`. Verified by
   inspection of `Anchor::new` / `Anchor::hash` / `commit_node`.
3. Doc note on `StateSnapshot::is_valid` flags the local-skew
   sensitivity for operators tuning `max_age_secs`.

The suwappu-dag side of B4 (named issue in `suwappu-node/events.rs:104` plus
broader clock-skew injection) is tracked in that repo.

## B5 — Key custody enforcement model

**Verdict:** ✅ Met (documentation clarification, no code change).

`docs/spec/key-custody.md` already specified the HSM-only profile as
binding. B5 adds an explicit **Enforcement model** section that
clarifies the layered responsibility:

- **Build:** no compile-time gate against `InsecureSoftKey` (test
  binaries + local-dev need the soft-key path).
- **Deploy:** Terraform / Helm / AMI tooling pins `KEY_SOURCE` env
  and excludes raw-key filesystem paths.
- **Runtime:** the attestation-handshake check in the failure-modes
  table rejects peers without an accepted `module_type` and refuses
  to start without a valid local attestation.
- **Audit:** the validator's attestation is mirrored to the
  on-chain anchor / governance log for off-chain forensic verify.

The rationale for **operational over code-level** is recorded
inline:

1. A compile-time gate adds ~½ sprint of cross-crate feature
   plumbing for something the runtime handshake already rejects
   *more strongly* — the runtime gate catches keys from any
   loader, not just the `InsecureSoftKey` path.
2. The attack surface that matters is the binary that actually
   ships to production rollout; that surface is bounded by
   deployment tooling, not by Cargo features.

Cross-references added: `docs/architecture/deployment-topology.md`
(deployment-layer specifics) and this ledger.

## B6 — Network endpoint auth posture

**Verdict:** ✅ Met. Landed on `hardening/b6-rpc-auth-bearer`.

Two complementary deliverables ship together:

### 1. In-process bearer-token middleware (defence-in-depth)

`crates/suwappudb-server/src/auth.rs` adds `BearerAuthConfig` +
`bearer_auth` middleware:

- `BearerAuthConfig::from_env()` reads `SUWAPPUDB_BEARER_TOKEN`. Unset
  or empty → disabled (pre-B6 behaviour preserved).
- Enabled config requires `Authorization: Bearer <token>` on every
  `/rpc` request. `/health` and `/metrics` stay open (liveness
  probes).
- Constant-time token equality (byte-OR accumulation) — denies
  timing side-channels.
- `with_token(string)` constructor for tests that don't mutate
  process-wide env (env-var mutation requires `unsafe` under Rust
  1.86+ and the workspace forbids `unsafe`).
- 4 unit tests cover default/disabled, with_token/enabled, and the
  constant-time comparator's match + length-mismatch paths.

### 2. Firewall / front-proxy documentation (primary control)

`docs/architecture/deployment-topology.md` gains a new "RPC
endpoint auth posture" section that makes the operator
responsibility explicit:

- Firewall / VPC SG is the primary control (Terraform modules
  configure it by default).
- Front-proxy with auth (nginx `auth_request`, Cloudflare Access,
  ALB authentication) is the recommended deployment pattern; an
  nginx snippet ships inline.
- Bearer token is the in-process **second layer** — treated like
  Postgres `password` auth, useful for accidental-exposure
  hardening, not load-bearing on its own.

When `SUWAPPUDB_BEARER_TOKEN` is set the binary logs
`Bearer-token auth ENABLED on /rpc`. When unset, the warning
explicitly names the firewall / front-proxy requirement and links
the deployment-topology doc.

### Documented divergences (accepted, not bugs)

| # | Divergence | Status |
|---|---|---|
| D1 | **Single-signer-per-chain (Rust) vs approved-set-per-chain (Solidity).** `VerifierConfig::EcdsaSecp256k1 { signer }` holds exactly one expected address; Solidity's `isApprovedSigner` is a set. The Rust verifier is strictly **stricter** — it rejects anchors signed by a non-registered key even if that key is in the on-chain approved set. The launch model has one HSM-bound signer per chain per [`docs/spec/key-custody.md`](../spec/key-custody.md), so the strictness matches the intended deployment. | ⚠ Accepted — by design |
| D2 | **BLAKE3-keyed MAC (Rust) ≠ keccak256 stub `computeMac` (Solidity).** Solidity's `computeMac` is a placeholder per its inline `TODO(S11)`. Real BLAKE3 on-chain needs a precompile; the cross-impl differential test bypasses MAC entirely (ECDSA signs the same EIP-191 payload on both sides; MAC is only used for in-process Blake3 chains). | ⚠ Documented in [`contracts/README.md`](../../contracts/README.md) "Parity model" |
| D3 | **`EthAddress` equality uses derived `PartialEq` (not constant-time).** Theoretical timing leak in `recovered == *expected_signer`, but approved signers are public on-chain (event log + `isApprovedSigner` mapping reader). An attacker doesn't need a timing oracle to enumerate them; the leak provides no incremental advantage. | ⚠ Accepted — exposure already-public |

### l1_reader

`crates/suwappudb-bridge/src/anchor/l1_reader.rs` was reviewed for B7
completeness. It carries a flagged TODO around HMAC key retrieval
that is intentional (the L1 reader was scaffolded against the
phase-1 BLAKE3-MAC path and gets re-pointed at the S11 verifier
config in a follow-on). Not a B7 finding — pre-existing scope.

### Recommendations follow-on (not blocking B7 close)

1. **Constant-time `EthAddress` compare.** Land a `subtle`-based
   equality helper to satisfy hygiene-conscious auditors even
   though D3 reasons it through.
2. **BLAKE3 precompile or keccak256 unification.** Pick a side and
   eliminate the Rust↔Solidity MAC divergence. Most likely path:
   switch the Rust BLAKE3 MAC to keccak256 since ECDSA chains
   don't use the MAC at all and Blake3 chains can be migrated
   alongside the LTP attestation path that already uses keccak.
3. **Approved-signer-set on Rust side.** Widen `VerifierConfig::EcdsaSecp256k1`
   to carry a `Vec<EthAddress>` (or `HashSet<EthAddress>`) so the
   Rust verifier and Solidity contract have identical signer-set
   semantics. Defer until the operations team needs multi-signer
   per chain.
